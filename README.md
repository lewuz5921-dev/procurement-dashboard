# 采购数字化数据看板 · Procurement Dashboard

> 🔗 **在线演示**：https://28be4b6812fa4504a05b91cd73b03cb4.app.workbuddy.link

## 关于作者与这个项目（请先读这一节）

本项目作者为**物流管理专业在读学生，没有采购岗位从业经历**。

看板基于物流管理专业课程框架（采购管理 / 供应商管理 / 供应链成本）与公开行业资料搭建，数据为模拟数据（`scripts/gen_data.py` 生成，含刻意埋入的业务异常）。

因此本项目**不主张"还原了真实采购场景"**，而主张以下三件事：

1. **采购核心指标的口径设计与可解释性** —— 每个指标都能说清"为什么这样算、分母为什么是它"；
2. **异常检测采用确定性规则引擎**，每条预警可追溯到明确的触发条件，规则代码与对外声明的口径严格一致；
3. **LLM 只做意图解析，答案由指标函数计算** —— 不做任何无出处的数字生成。

附「[口径 revision：节约率从 v1 到 v2](#口径-revision节约率从-v1-到-v2)」一节，记录了一次**被自己发现的指标口径错误**及其修正过程。

## 技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| 前端 | Vue 3 + Vite | 组合式 API + 路由，组件化 |
| 可视化 | ECharts 5 | 柱/线/饼/散点/雷达/堆叠图 |
| 数据 | 本地 JSON 模拟集 | 由 `scripts/gen_data.py` 生成，1008 条订单（含物料与基准价字段）+ 20 家供应商 |
| 检测 | 规则引擎（纯 JS） | 可解释的确定性规则，见 `src/utils/rules.js` |
| AI | DeepSeek + Function Calling | 自然语言问数：LLM 只做意图解析，答案来自指标函数 |

**数据分层设计**：数据加载层（`src/data/store.js`）与指标计算层（`src/utils/metrics.js`）解耦。真实场景下，仅需将 `store.js` 中的本地 fetch 替换为后端 API（如 Java/SQL 数据服务），指标计算逻辑不变。

## 页面信息架构（主线收敛）

六个页面全部保留，但**只有一条主线**，其余降级为下钻页 —— 因为看板的价值不在"能看多少"，而在"看完知道该干什么"。

```
采购总览（发生了什么） ──► 智能洞察（为什么） ──► 智能问答（直接问数）
   │
   ├─ 准时交付率 OTD 卡 ──────► 履约监控（下钻，可带 ?supplier=A01 预选供应商）
   ├─ 成本节约卡 ────────────► 成本分析（下钻）
   ├─ 供应商帕累托卡 ────────► 供应商评估（下钻）
   └─ 异常预警卡 ────────────► 智能洞察（下钻）
```

- 首页第一屏的**每张 KPI 卡都自带"下一步去哪看"**，点击即下钻，不做平级导航；
- 第一屏下半部分最显眼的位置留给**一条单供应商的 OTD 趋势**（华信精密 91.1% → 13.6%），配一句可执行结论；
- 下钻页顶部均提供「← 返回总览」。

## 指标口径表（面试核心）

| 指标 | 计算公式 | 业务含义 |
|------|---------|---------|
| 采购总金额 | Σ(单价 × 数量) | 采购规模 |
| 准时交付率 OTD | 按时到货订单数 / 总订单数 × 100% | 供应商交付可靠性 |
| **OTD 目标差距** | 目标 90% − 实际 OTD（百分点） | 还差多少才达标 |
| **OTD 拖累归因** | 某供应商逾期订单数 / 全量订单数 × 100（pt） | 谁在拉低整体 OTD，各项可加和、可排序 |
| 验收合格率 | 质量合格订单数 / 总订单数 × 100% | 来料质量水平 |
| 平均交付周期 | Σ实际交付天数 / 订单数 | 履约效率 |
| 供应商集中度 | TOP 供应商金额 / 品类总金额 | 依赖风险（>60% 预警） |
| **成本节约率 v2** | Σ(基准单价 − 成交单价) × 数量 ÷ Σ(基准单价 × 数量) | 相对独立基准价的议价收益，**分母用基准口径总额** |
| **基准覆盖率** | 有基准价的订单数 / 总订单数 | 该节约率能代表多少订单，**必须与节约率同时展示** |
| TCO 全生命周期成本 | 单价 × (1 + 运输费率 + 质量损失率 + 交易管理费率) | 打破「单价最低」直觉 |
| 帕累托累计占比 | 按金额降序累加 / 总额 | 识别核心供应商 |

### 基准价取数口径（四级优先级）

`scripts/gen_data.py` 的 `attach_benchmarks()` 为每笔订单挂载 `benchmarkPrice` + `benchmarkSource`：

| 优先级 | 基准来源 | 字段 | 取数规则 |
|---|---|---|---|
| ① | 年度框架合同价 | `contract_price` | 「品类 × 供应商」年初签订、全年固定、**不随行就市**；一旦有合同价优先使用 |
| ② | 上次成交价 | `last_deal_price` | 同物料 + 同供应商最近一次成交（**3 个月内**），按品类行情指数折算到本期口径 |
| ③ | 当期询价最低有效报价 | `best_quote` | 本期询价中的最低有效报价，围绕当期市场参考价竞争得出 |
| ④ | 滚动 12 个月成交均价 | `hist_avg_12m` | 同物料 + 同供应商近 12 个月成交均价（**不含当期**，样本 ≥3 笔），折算到本期口径 |

三条硬约束：

- **基准不与被评估订单同源。** 基准取自其他时点 / 其他主体 / 事先约定的价格，按时间顺序逐单取数、**不使用本单之后的信息**（无前视偏差）；
- **无基准价的订单不参与计算、也不补默认值。** 宁可少算，不可假算；
- **覆盖率低于 60% 时直接显示「基准价缺失，暂不可计算」**，不用 0 或均价顶上。假数字比没有数字更危险。

## 异常检测规则引擎

| 规则 | 触发条件 | 阈值 |
|------|---------|------|
| R1 OTD 连续下滑 | 近 3 个月 OTD 较前 9 个月基线下降 | > 20 个百分点 |
| R2 报价离群 | 供应商成交均价 vs **同品类其他供应商**均价（**留一法**，剔除自身样本） | > 2σ |
| R3 单一供应商依赖 | 单一供应商占品类采购额 | > 60% |
| R4 低价高 TCO | 单价低于品类均值 15% 且 TCO 高于品类均值 | 双条件 |

> R2 的「留一法」是修正后的口径：把候选供应商自己的订单算进品类 σ，它会把自己的离群"洗白"
> —— 实测鑫源材料（A12）在含自身口径下仅 **+1.50σ**（不触发），留一法口径下为 **+2.57σ**（触发）。
> 规则代码必须与对外声明的口径严格一致，这一条已写进 `src/utils/rules.js` 的注释。

每条预警均含「归因分析 + 优化建议」，可追溯到明确触发条件（可解释 AI 原则）。

## 口径 revision：节约率从 v1 到 v2

> 这一节记录了一次**被自己发现的口径错误**。保留错误、写清修正过程，是因为它比"结果好看"更能说明方法是否可靠。

### v1 口径（已废弃）

```
节约率 = Σ(品类均价 − 成交单价) × 数量 / 总金额
```

它站不住的原因不是"数字偏大偏小"，而是**数学上恒等于 0**。品类均价本身就是这批订单的数量加权均价，代进去：

```
Σ(均价 − 单价ᵢ) × 数量ᵢ
= 均价 × Σ数量ᵢ − Σ(单价ᵢ × 数量ᵢ)
= Σ(单价ᵢ × 数量ᵢ) − Σ(单价ᵢ × 数量ᵢ)
= 0
```

即「拿自己当基准量自己」。而线上页面当时显示的是 **0.3%** 而不是 0% —— 这个差值本身就是一个信号：说明中间有一步不是数量加权（当时实现用的是**未加权算术平均**，与分母的加权口径不一致）。不管哪种情况，这个数字都**不能作为"节约"对外呈现**。

更根本的问题：真实采购不拿"当期均价"当基准。拿一批订单自己的平均值当靶子，这叫自说自话。

### v2 口径（现行）

引入独立的**基准单价 `benchmark_price`**，四级优先级取数（见上文「基准价取数口径」）：

```
节约额 = Σ(基准单价ᵢ − 成交单价ᵢ) × 数量ᵢ          （仅计有基准价的订单）
节约率 = 节约额 / Σ(基准单价ᵢ × 数量ᵢ)              （分母用基准口径总额）
```

**分母为什么用基准口径总额？** 它代表"不省的话要花多少"。若改用实际总额，分母更小、节约率会被放大 —— 两种口径行业内都有人用，**本项目的选择是基准口径总额，并在此写明**。

**为什么 v2 不会重蹈恒等于 0 的覆辙？** 关键不是"基准是否来自本项目的数据集"（模拟数据不可能有外部真值），而是**基准不与被评估订单构成同一求和项**：① 是事先约定的合同价，②④ 取自**其他时点**的成交，③ 取自**当期市场**的最低报价。它们都不是"这一单自己"。

### 覆盖率机制（与 v2 同时引入）

不是每笔订单都有基准价，所以**报节约率时必须同时报覆盖率**：

```
节约率 1.78%（基准覆盖率 77.8%，224 单无基准价未计入）
```

- 无基准的订单**不参与**节约率计算，也**不补默认值**（不用 0、不用均价顶上）；
- 覆盖率低于 60% 时，页面直接显示 `基准价缺失，暂不可计算` —— 假数字比没有数字更危险；
- 覆盖率本身也要能解释：模拟数据里它由三个参数决定（`scripts/gen_data.py` 顶部常量，可调参复现）：
  `FRAME_P = 0.52`（品类×供应商已签框架协议比例）、`RECORD_P = 0.65`（该组合是否已维护基准价档案）、
  `RFQ_P = 0.55`（物料是否纳入询价池）。现实中基准价不是自动就有的，需要采购员在系统里维护，
  维护完整度低正是本页面强制显示覆盖率的原因。

### 拆开看才有信息量

单一节约率数字藏得住问题，拆开就藏不住 —— 当前数据的四类基准口径结果完全不同：

| 基准来源 | 订单数 | 基准金额 | 节约额 | 节约率 | 说明 |
|---|---|---|---|---|---|
| ① 年度框架合同价 | 441 | ¥983.2 万 | ¥38.3 万 | **+3.90%** | 合同价口径的降本率 |
| ② 上次成交价 | 181 | ¥568.1 万 | ¥5,909 | **+0.10%** | 剔除行情后与上次基本持平 → 议价能力没有改善 |
| ③ 当期询价最低报价 | 159 | ¥410.2 万 | −¥3.9 万 | **−0.95%** | 成交价**高于**当期最低有效报价 → 询价环节仍有下探空间 |
| ④ 滚动 12 个月均价 | 3 | ¥2.4 万 | −¥279 | **−1.17%** | 样本不足，仅作兜底 |
| **合计（已覆盖）** | **784** | **¥1963.9 万** | **¥35.0 万** | **+1.78%** | 覆盖率 77.8%，224 单无基准价未计入 |

### 一句话结论

v1 错的不是"算得不准"，而是**结构上不可能算对**；v2 换了基准，并且强制把"能代表多少订单（覆盖率）"和"每一类基准各自表现如何（分来源）"一起报出来 —— 一个不敢拆开的指标，本身就不该被信任。

### 订单数据字段

存量字段（`id / month / date / supplierId / supplierName / category / qty / unitPrice / amount / leadDays / actualLeadDays / onTime / qualityPass`）之外，本次为节约率 v2 新增 3 个字段：

| 字段 | 含义 | 缺省值 |
|---|---|---|
| `material` | 物料规格档（每品类 4 档，按基准口径单价分位确定） | 必有 |
| `benchmarkPrice` | 基准单价；取不到时为 `null` | 可为 `null` |
| `benchmarkSource` | 基准来源枚举（`contract_price` / `last_deal_price` / `best_quote` / `hist_avg_12m`） | 可为 `null` |

> 生成器改造时使用了**独立随机流**（`random.Random(2026)`），因此新增字段不影响既有成交数据的随机序列——存量 1008 单的单价 / 数量 / 履约表现**逐位未变**。

## 部署

构建产物为纯静态文件（`dist/`），可部署到任意静态托管：GitHub Pages / Vercel / Netlify / Cloudflare Pages。

- GitHub Pages：仓库 Settings → Pages → 选择 `main` 分支 `/docs` 或启用 Actions 部署 `dist/`
- 注意 `vite.config.js` 已设置 `base: './'`，支持子路径部署
- **⚠️ 安全提示**：`VITE_DEEPSEEK_API_KEY` 会被打进构建产物。公开部署前请勿带 key 构建（无 key 时自动降级为规则解析），或改用后端代理（如 Cloudflare Worker）转发请求以保护密钥。
